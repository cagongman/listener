1 · Bot Mode와 전문 역할

모니카·키워드·주식 봇을 독립 프로필과 관리되는 Bot Chat으로 구성합니다. 모니카가 요청을 배분하고 결과를 종합합니다. 일반 CLI 세션과 봇의 고정 대화를 구분합니다.

2 · 스킬과 데이터 도구

스킬에는 분석 절차와 답변 형식을 둡니다. 시세는 API/MCP 도구로 가져오며 출처·기준 시각·지연 여부·캐시 상태를 함께 반환합니다.

3 · n8n으로 반복 실행

예약 수집과 조건 알림을 구성합니다. 공통 작업 ID로 재시도와 중복을 관리하고, 인증된 웹훅이나 필요한 MCP 도구만 연결합니다. 실시간 체결 수집은 별도 스트림 수집기를 검토합니다.

단계별 구현·검증 계획 ↗

자동 검증 51개 통과. 실제 Gateway에서 같은 세션의 첫 요청 started / 두 번째 queued 상태를 확인했고, 두 요청 모두 completed로 끝났습니다. 배포 앱은 공유 large-v3 CUDA에 연결해 음성 대기 중입니다. 봇·시세 API·n8n은 다음 단계에서 연결합니다.

01.1 — PROCESS & DATA ARCHITECTURE

프로세스를 나누고, 자원은 한곳에.

두 UI 앱과 공통 음성 서비스가 독립적으로 실행됩니다. Hermes CLI는 음성 호출 앱이 필요할 때 여는 별도 프로세스입니다.

자식 실행: Hermes CLI · 별도 터미널 ↗
앱 ↔ 서비스: 사용자 범위 Named Pipe / JSON 요청·이벤트 / 요청 ID + 세션 ID

PCM은 서비스 내부에, 텍스트와 제어 메시지는 IPC에. UI 프로세스는 마이크 스트림이나 WhisperModel을 만들지 않습니다. 서비스만 공통 설정과 모델 전환을 조정하고, 호출어 규칙과 CLI 실행 설정은 Hermes 앱이 관리합니다.

음성 서비스 안에서도 입력과 추론을 분리합니다.

AUDIO CALLBACK

입력을 빠르게 보관

마이크 콜백은 프레임 ID와 PCM을 제한된 버퍼에 보관합니다. 콜백 안에서 Whisper 추론이나 CLI 실행을 기다리지 않습니다.

VAD / SESSION WORKER

발화를 자르고 작업 생성

버퍼를 읽어 발화 시작·종료를 검출합니다. 겹치는 탐색 구간, 녹음 범위, 다음 명령의 오디오를 프레임 시각으로 연결합니다.

SINGLE INFERENCE WORKER

한 모델에서 순서대로 추론

핫키 받아쓰기 → 활성 명령 → 호출어 탐색 순으로 대기 작업을 선택합니다. 이미 실행 중인 추론은 종료 후 다음 작업으로 넘어갑니다.

“헤이 모니카” 다음에 명령을 말했을 때의 통신 흐름

호출 감시 등록 → 텍스트 이벤트 → 명령 수집 → CLI 실행
순서보내는 곳 → 받는 곳처리 내용
01Hermes 앱 → 음성 서비스subscribe_wake로 호출 감시를 등록합니다. 두 앱 모두 서비스가 없으면 먼저 시작한 뒤 연결합니다.
02마이크 → VAD → Whisper음성 구간을 탐색 작업으로 만들고 인식합니다. 이 과정에서도 다음 음성 프레임은 계속 버퍼에 쌓입니다.
03음성 서비스 → Hermes 앱utterance 이벤트로 인식문, 구간 ID, 시작·종료 프레임과 인식 메타데이터를 전달합니다.
04Wakeword → Command session“헤이 모니카”를 판별하고 확인음을 냅니다. 호출어 뒤에 명령이 이미 있으면 추가 녹음 없이 프롬프트로 사용할 수 있습니다.
05Hermes 앱 → 음성 서비스호출어만 있다면 arm_command로 다음 발화를 요청합니다. 호출 구간 이후의 프레임을 이어 받고 5초 이내 시작된 발화를 수집합니다.
06음성 서비스 → Hermes 앱transcript로 명령 텍스트를 반환합니다. 타임아웃·버퍼 유실·길이 초과는 구분해 알리고 잘린 명령은 실행하지 않습니다.
07SessionController → Hermes Gateway선택한 세션 ID와 입력 ID로 명령을 접수하고 결과를 기록합니다. 호출만 한 경우 같은 세션의 CLI 화면을 열며, 작업 중 후속 요청은 대기열에 보존합니다.

앱 → 서비스: 제어 요청 예시

원본 음성을 전송하는 대신 세션과 녹음 범위를 지정합니다. 아래는 구현한 메시지의 핵심 필드입니다.

  "type": "arm_command",
  "request_id": "req-007",

서비스 → 앱: 명령 인식 완료 예시

요청·세션 ID로 결과를 연결합니다. 취소되거나 이전 세션에 속한 늦은 결과는 사용하지 않습니다.

{
  "version": 1,
  "type": "transcript",
  "request_id": "req-007",
  "session_id": "wake-042",
  "status": "ok",
  "text": "이 프로젝트 설명해 줘"
}

Hermes 앱의 기본 상태 전이

LOADING→LISTENING→ARMED→CAPTURING→LAUNCHING→COOLDOWN↩ LISTENING

호출과 명령을 함께 말하면 ARMED·CAPTURING을 건너뛸 수 있습니다. 호출만 하고 다음 말이 없으면 ARMED에서 CLI 실행으로 넘어갑니다. 핫키 녹음은 현재 음성 세션을 취소하고 감시를 일시 중지하며, 서비스 장애는 ERROR 상태로 표시합니다.

장애 경계를 분리합니다. Hermes CLI가 종료되거나 실행에 실패해도 마이크와 받아쓰기 서비스는 유지합니다. 공통 음성 서비스가 중단되면 두 앱 모두 오류를 표시하고 재연결하되, 이전 명령을 자동 재실행하지 않습니다.
02 — USER FLOW

짧게 부르거나, 바로 부탁하거나.

두 가지 호출 방식을 지원합니다. 호출어를 판별하는 동안 들어온 다음 음성도 버퍼에 보관해 명령이 끊기지 않게 합니다.

“헤이 모니카”

헤이 모니카 …

B / 호출어 + 명령을 한 번에

“모니카, 프로젝트 설명해 줘”

모니카, 프로젝트 설명해 줘
  1. 발화 시작에서 호출어 확인호출어와 이어지는 명령을 분리
  2. 선택한 대화에 JSON-RPC로 전달접수 ID를 저장하고 알림 표시
  3. 같은 대화에서 응답 확인작업 중에는 다음 요청으로 접수
prompt.submit · session_id · input_id인증된 Gateway

호출어 판별: 발화 시작에서만 검사하고 “헤이 모니카”를 우선 매칭합니다. “하모니카”, “모니카가 말했다” 같은 일반 문장을 제외하며, 한 번의 호출로 한 번만 실행하도록 중복 이벤트를 제거합니다.

서비스는 자동으로 연결하고 정리합니다.

먼저 실행된 앱이 서비스를 시작하고 나중 앱은 연결합니다. 마지막 앱 종료 후 30초 유예를 거쳐 종료합니다. 장애 시 유실된 Hermes 명령을 자동 재실행하지 않습니다.

창과 대화 세션을 따로 관리합니다.

대화 ID로 후속 입력을 보내고 CLI 화면은 같은 ID로 엽니다. 저장된 선택을 재개하며 임의의 최신 대화로 보내지 않습니다. 봇·n8n 연결과 응답 TTS는 후속 확장입니다.

1차는 VAD + 기존 Whisper를 사용합니다. VAD는 발화 유무를 감지하고 Whisper는 호출어와 명령을 텍스트로 인식합니다. 무음 제거 옵션만으로 연속 마이크의 발화 검출이 완성되지는 않습니다.

large-v3로 주변 발화를 계속 해석하는 비용과 짧은 “모니카”의 오탐이 주요 제약입니다. 창 길이·beam_size·발화 종료값을 조정한 뒤에도 목표에 미달하면 전용 한국어 호출어 감지기를 앞단에 추가하고, 명령 STT는 공유 Whisper를 유지합니다.

오디오 버퍼는 메모리 크기를 제한합니다. 최대 길이 초과·버퍼 유실 시 잘린 명령을 실행하지 않습니다. 원본 오디오를 디스크에 저장하지 않고 전체 인식문도 기본 로그에서 제외합니다.
